# TRMNL Running Board Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A private TRMNL plugin that shows this week's Tredict training, an estimated form graph and today's run window
on one full 800x480 screen.

**Architecture:** The display logic lives in small browser-safe JS modules under `integrations/trmnl-running-board/src/`,
unit-tested with Jest in Node. A build script inlines them into `shared.liquid`, which embeds the polled responses and
renders the screen. A liquidjs + `vm` harness, copied from eu-dayahead, renders the real templates against fixtures.

**Tech Stack:** Liquid (TRMNL, framework 3.4.0), plain ES2023 browser JS, Highcharts 12.3.0 from TRMNL's CDN, Jest,
liquidjs, js-yaml.

**Spec:** `docs/superpowers/specs/2026-11-02-trmnl-running-board-design.md` (approved 2026-11-03).

## Global Constraints

- Node >= 22, CommonJS for Node files, Jest, ESLint + Prettier: single quotes, semicolons, 2-space indent, no trailing
  commas, max 120 cols.
- Plugin files (`settings.yml`, `shared.liquid`, `full.liquid`) are each ≤ 100 KB. Only `full` layout in v1.
- No weather logic in the plugin: every window, rain chance and wind value comes from the run-window API response.
- "dry" / "droog" only when `qualifies` is true and `precipProbMax <= 20`; otherwise "rain N%" / "regen N%".
- The form is always labelled "Form (est.)" / "Vorm (schatting)".
- Committed Tredict fixtures are synthetic: Tredict's structure, invented ids, dates, titles, notes and metrics, no
  token. Real responses only in the gitignored `tests/fixtures/private/`; `npm test` passes without it.
- No token, real coordinate or personal name anywhere in the repo. Examples use Amsterdam centre (52.37, 4.89).
- Quote every select value in `settings.yml`.
- 1-bit output: black and white only, animations off, chart IDs via `append_random`.
- Strings in en and nl; unsupported locales fall back to en. Times and numbers via `Intl` in the resolved language.
- Garmin `attribution` text is shown whenever a shown activity has `isFromGarminApi: true`; the API's `attribution` is
  shown whenever the run window is shown.

## Review Focus

1. Tredict text containing `<`, `</script>`, quotes or emoji in a title or note → shown as plain text, page intact.
2. A Tredict 5xx, timeout or unexpected body on one of IDX 0–2 (not 401/403) → that data's panel says "Tredict
   unavailable", the rest renders.
3. Day boundaries: an activity at 23:30 local on Sunday and one at 00:30 local on Monday land on the right days and
   weeks, including the week a DST change falls in.
4. A new account (no efforts, no activities, no plans) → empty states, never `NaN`, `undefined` or a blank graph.
5. Optional fields missing (a plan with distance but no duration; an activity without heart rate or pace) → that part
   is left out, never printed as `undefined`/`NaN`/`0:00`.

Each has a test in the task that owns the code (marked "Review Focus N").

## Decisions this plan makes

- **Copy for a shorter window:** "Only {n} min fits your hours", not the spec's example "Only 45 min dry in your
  hours": a qualifying window can have up to the user's rain limit, so "dry" there could contradict the API's rule.
- **Tredict range:** IDX 0 asks from the day before this local Monday to the day after next Monday, and the JS filters
  by local date. This covers tomorrow on a Sunday, and makes an offset or DST error in the URL harmless.
- **Timezone:** the user's `trmnl.user.time_zone_iana` (name confirmed in V4); if absent, the run-window response's
  `location.timezone`; else `UTC`.
- **Form model:** CTL += (load − CTL)/42, ATL += (load − ATL)/7, form = CTL − ATL of the same day, both starting at 0 on
  the first day with data. Past days use confirmed efforts only; today and later add `unconfirmed` ones. The
  constants are exported so V10 can try variants.
- **Which day and length:** see Task 6; it implements the spec's "Run window" section as one function.
- **Rest day:** a day with no planned session of the filtered sport.
- **Missed:** a plan on a past day with no `executedTrainingId`.
- **Source layout:** `src/` is not uploaded to TRMNL; only `settings.yml`, `shared.liquid` and `full.liquid` are.

## File Structure

```
integrations/trmnl-running-board/
  settings.yml                 TRMNL settings: polling URLs, headers, custom fields, refresh
  shared.liquid                GENERATED by scripts/build-trmnl.js; do not edit
  full.liquid                  one call: window.renderRunningBoard({ ... sizes })
  src/shared.template.liquid   markup, styles, data embedding; `/* @modules */` marks where modules go
  src/strings.js               STRINGS (en, nl), resolveLanguage, fill
  src/time.js                  local-date helpers, ISO week, availability end
  src/responses.js             normalise a polled or fetched value into ok/error
  src/week.js                  calendar rows and footer totals
  src/form.js                  daily load and form series
  src/runWindow.js             which day, which length, what the panel says
  src/render.js                DOM output and the Highcharts config; defines window.renderRunningBoard
scripts/build-trmnl.js         inlines src/*.js into shared.liquid
tests/trmnl/harness.js         liquidjs + vm harness (from eu-dayahead), IDX_0..3, fixed clock, optional fetch
tests/trmnl/preview.js         writes one HTML page per case, for a real-browser check
tests/trmnl/formCheck.js       local only: compares form with values read from the Tredict app
tests/trmnl/*.test.js          unit and render tests
tests/fixtures/tredict/        synthetic Tredict responses
tests/fixtures/trmnl/          run-window responses for the plugin cases (from the live API shape)
docs/superpowers/specs/2026-11-03-trmnl-running-board-verify.md   answers to V1–V10
```

Module rules (Task 2 enforces them): each `src/*.js` file has no `require` other than lines of the form
`const { a, b } = require('./other');`, defines its functions at top level with names unique across all modules, and
ends with exactly one line `if (typeof module !== 'undefined') module.exports = { ... };`. The build strips both kinds
of line and concatenates the modules, in the order strings, time, responses, week, form, runWindow, render, into one
IIFE.

### Task 6: Run window panel

**Files:**
- Create: `src/runWindow.js`, `tests/fixtures/trmnl/window-*.json`, `tests/trmnl/runWindow.test.js`

**Interfaces:**
- Consumes: `availabilityEnd`, `localDate`, `addDays`, `normalise`.
- Produces: `pickSession({ plans, today, tz, now, avail, sport }) -> { day: 'today'|'tomorrow', minutes: number|null, reason: 'planned'|'noDuration'|'noPlan', overLimit: boolean }`
  and `windowPanel({ result, session, language, hasLocation }) -> Panel`, where `result` is `normalise()` of the
  run-window response and
  `Panel = { kind: 'window'|'shorter'|'fallback'|'none'|'error'|'noLocation', heading, lines: string[], stale: boolean }`.

`pickSession`, in this order (spec "Run window"):
1. Past today's hours = `now` > `availabilityEnd(avail, today, tz)`.
2. Remaining today = plans today for the sport with no `executedTrainingId`, earliest first.
3. Not past and a remaining plan → today, that plan.
4. Else the first plan tomorrow for the sport → tomorrow, that plan.
5. Else → `noPlan`, 60 minutes, on today if not past and today had no plan, otherwise tomorrow.
A plan's `minutes` = `duration / 60` rounded up to 15, min 15; over 180 → 180 with `overLimit`. No duration →
`noDuration`, 60.

`windowPanel` picks `days[0]` or `days[1]`, then `windows[String(minutes)]`; if null, the longest shorter non-null key
(`shorter`), else `fallback` (`fallback`), else `none`. Lines: time range in `location.timezone`; rain wording per the
global rule; `{windAvg} km/h {windFromCardinal} · {apparentTempAvg}°C`; "start into the wind ({windFromCardinal})";
"dark after HH:MM" from that day's `sunset` when not null. `stale` when `warnings` includes `stale_data`.
